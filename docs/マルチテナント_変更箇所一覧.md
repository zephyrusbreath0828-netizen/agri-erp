# マルチテナント化 改修（ver 3.4）

## 目的
1つの Supabase を複数組織（テナント）で共用し、各組織が自組織のデータのみ参照・編集できるようにする。
画面（フロント）と DB（RLS）の二段で隔離する。

## 階層構造
```
Organization（organizations）
└ Company（companies）
   └ Branch（branches）
```
会社・拠点マスタ、帳票テンプレートは既存のまま維持し、すべて `organization_id` で所属組織に紐付ける。

## データアクセス制御（フロント）
1. ログイン時、`users.organization_id` を `Auth.user.organizationId` に保持（`Tenant.id()`）。
2. `Tenant.enter(user)` が `Store.db` の各配列を自組織の行だけにスコープする（他組織データはクライアントに残さない）。
3. 全画面・帳票・CSV は `Store.db` を参照するため、追加のフィルタ実装なしで自動的に隔離される。
4. 新規登録は `Store.save()` の `Tenant.stampAll()` が `organization_id` を自動付与（入力不要）。
5. 採番（`number_sequences`）も `o{組織ID}:{prefix}-{日付}` のキーで組織別。

## データアクセス制御（DB / RLS）
- 全業務テーブルで `organization_id` を NOT NULL + FK。
- `alter table ... enable row level security` + `tenant_isolation` ポリシー（`using` / `with check` とも `organization_id = current_org_id()`）。
- `current_org_id()` は次の順で解決：
  1. Supabase Auth の JWT（`app_metadata.organization_id` / `user_metadata.organization_id`）
  2. カスタムログインのセッショントークン（`x-app-token` ヘッダ → `app_sessions`）
- `app_sessions` は RLS 有効・anon/authenticated への権限剥奪。トークン発行は `SECURITY DEFINER` の `app_login()` のみ（bcrypt 照合もサーバー側）。
- トリガ `tenant_stamp`（未指定なら現在組織を自動付与）と `tenant_guard`（`organization_id` の変更を拒否）でアプリを迂回した越境も防止。
- `organizations` は参照=自組織（またはシステム管理者）、追加/編集/停止=システム管理者のみ（`is_system_admin()`）。

## 既存データ移行
1. `sql/08_multi_tenant.sql` を実行すると、既存の全行が `organization_id = 1`（SETOLAS）へ割当てられる。
2. アプリ側でも `Store.migrateTenant()` が null 行を 1 に補完するため、SQL 未実行環境でも動作する。
3. 会社・拠点・帳票テンプレートは従来どおり利用可能（組織内に閉じる）。

## 管理機能
- 「システム → 組織マスタ」を追加（`roles: ['admin']` + `sysOnly`）。
- システム管理者（`users.is_system_admin` または緊急管理者）のみ：組織追加／編集／停止が可能。
- ログイン中の組織は停止不可、有効な組織が1つだけの場合も停止不可。

## 運用上の注意
- 既存DBへ適用する順序：`sql/08_multi_tenant.sql` → アプリ（`build/agri-erp-supabase.html`）差し替え。
- RLS を有効にした後は、`app_login` で取得したトークンを `x-app-token` で送る本アプリ経由でのみデータへ到達できる（anon キー単体では 0 行）。
- Supabase Auth へ移行する場合は、`app_metadata.organization_id` に組織IDを設定すれば同じポリシーで動作する（カスタムアクセストークンフック推奨）。
